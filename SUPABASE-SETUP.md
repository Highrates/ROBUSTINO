# Настройка Self-Hosted Supabase: одна БД для локалки и прода

Supabase развёрнут на вашем сервере. Чтобы и локальная разработка, и прод использовали одну БД и загрузка файлов (в т.ч. 3D моделей) работала везде — выполните шаги по порядку.

---

## Шаг 1. Переменные окружения (одна БД для всех)

Одинаковые значения для **локальной** и **продакшен** среды.

### Локально

1. В корне проекта скопируйте пример и отредактируйте:
   ```bash
   cp .env.example .env
   ```
2. В `.env` укажите URL и anon key вашего Supabase:
   ```env
   VITE_SUPABASE_URL=https://ваш-домен.ru/supabase-api
   VITE_SUPABASE_ANON_KEY=ваш_anon_key
   ```
   Или с IP, например: `http://194.67.124.92/supabase-api` — в зависимости от того, как открывается API на сервере.

### На проде (сервер, где крутится фронт)

В среде, где запускается приложение (pm2, systemd, или переменные при `npm run build`), задайте **те же** переменные:

- `VITE_SUPABASE_URL` — тот же URL, что и в `.env` локально  
- `VITE_SUPABASE_ANON_KEY` — тот же ключ  

Так и локально, и на проде будет использоваться одна БД.

---

## Шаг 2. CORS и лимит загрузки на сервере (nginx)

Чтобы браузер с `http://localhost:3000` и с прода (robustino.ru) мог обращаться к Supabase API и загружать файлы, в nginx нужно разрешить оба origin и увеличить лимит тела запроса.

### Готовые правки для вашего сервера

**Вариант А — скрипт (все три шага одной командой):**

1. На сервере перейдите в папку проекта (или скопируйте туда `scripts/apply-nginx-supabase-cors.sh`).
2. Выполните:
   ```bash
   sudo bash scripts/apply-nginx-supabase-cors.sh
   ```
   Скрипт создаёт резервную копию конфига, добавляет `map` для CORS, подменяет оба блока `location /supabase-api/`, проверяет nginx и перезагружает его.

**Вариант Б — вручную:**

В репозитории есть файл **`nginx-supabase-cors.conf`** с готовыми фрагментами. На сервере отредактируйте `/etc/nginx/sites-available/default`:

1. **В начало файла** (сразу после блока комментариев, перед первым `server {`) вставьте блок `map` из `nginx-supabase-cors.conf` (раздел 1).

2. **Замените оба блока** `location /supabase-api/ { ... }` (в default_server на 80 и в server robustino.ru на 443) на блок из `nginx-supabase-cors.conf` (раздел 2). В нём уже есть:
   - `client_max_body_size 50M;` — загрузка 3D моделей без 413
   - CORS-заголовки для `https://robustino.ru` и `http://localhost:3000`
   - обработка `OPTIONS` для preflight

3. Проверка и перезагрузка:
   ```bash
   sudo nginx -t && sudo systemctl reload nginx
   ```

### Общий вариант (любой домен)

Если настраиваете другой сервер/домен, в начале конфига (вне `server`) добавьте:

```nginx
map $http_origin $cors_origin {
    default "";
    "https://ваш-прод-домен.ru" $http_origin;
    "http://localhost:3000" $http_origin;
}
```

В `location /supabase-api/` добавьте `client_max_body_size 50M;`, CORS-заголовки и обработку OPTIONS, как в `nginx-supabase-cors.conf`.

## Шаг 3. Лимит размера тела (загрузка 3D моделей)

Ошибка **413 Payload Too Large** при загрузке GLB значит, что лимит размера тела запроса на сервере меньше размера файла. Нужно увеличить лимит в том же nginx (или в другом прокси перед Supabase).

В `server` или в `location`, обрабатывающий запросы к API/Storage, добавьте или измените:

```nginx
client_max_body_size 50M;
```

При необходимости можно поставить больше (например `100M`). Перезапуск nginx — как в шаге 2.

---

## Проверка

1. **Локально:** запустите приложение (`npm run dev`), откройте админку, загрузите 3D модель — не должно быть CORS и 413.  
2. **Прод:** откройте продовый сайт, убедитесь, что данные те же (одна БД) и загрузка тоже работает.

Если что-то из шагов делается не в nginx (другой прокси, облачный балансировщик), те же идеи применяются там: разрешить origin прода и `http://localhost:3000`, увеличить лимит размера тела запроса.
